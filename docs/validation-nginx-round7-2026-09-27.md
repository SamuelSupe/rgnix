# 最新 rgnix 源码与 NGINX 对比 — 2026-09-27

**第七轮优化后的 rgnix 仍明显落后于 NGINX。** 双 worker、64 并发时，普通 1 KiB HTTP 代理为 **93,348 / 233,617 请求/秒**，NGINX 约为 rgnix 的 **2.50 倍**；静态文件为 **3.27 倍**，请求头分流为 **3.18 倍**。以下均为本次交替运行的三轮中位数，没有将旧 NGINX 数据与新 rgnix 数据拼接。

12 个场景/并发组合中，NGINX 三轮的最低吞吐均高于 rgnix 三轮的最高吞吐。这支持本次环境下存在明显差距的判断。但同一 rgnix 二进制的 A/A 校准最大相邻差异为 **25.54%**，整体未通过稳定性门槛，倍数应视为短时观测值，不能作为容量保证或精确的优化归因。

本次比较的是第七轮**未发布工作区二进制**与固定版本 **NGINX 1.30.5**。第七轮报告的健康检查场景 +66.3% 是 rgnix 自身的前后对比；本次六类负载没有开启主动健康检查，不能将那个收益外推为对 NGINX 的提升。

完成 **72 个正式对照窗口、116,284,920 次请求，HTTP/连接/读/写/超时错误均为零**。另有 12 个 A/A 窗口、9,003,148 次请求，错误也为零。共 84 个窗口、125,288,068 次请求；预热、预检及上游校准不计入这些总数。

## 延迟、CPU 与内存

P99 单位为毫秒，表示三轮窗口 P99 的中位数，不是将所有请求合并后的全局 P99。wrk 使用固定并发的闭环负载；这些值不代表固定到达速率下的 SLO。

| 场景 | rgnix P99 / c64 | NGINX P99 / c64 | rgnix P99 / c256 | NGINX P99 / c256 |
| --- | ---: | ---: | ---: | ---: |
| 直接响应 | 1.154 | 1.148 | 2.239 | 1.581 |
| 静态文件 | 1.487 | 0.701 | 11.358 | 1.693 |
| 1 KiB HTTP 代理 | 1.775 | 1.001 | 8.257 | 2.243 |
| 16 KiB HTTP 代理 | 2.454 | 1.121 | 7.833 | 4.356 |
| 请求头分流 | 1.997 | 0.960 | 7.622 | 2.085 |
| HTTPS 代理 | 3.008 | 1.120 | 10.353 | 3.134 |

必须保留的尾延迟窗口：

- rgnix 的 256 并发静态文件 P99 三轮为 **21.242、10.330、11.358 ms**，NGINX 为 **1.402、2.520、1.693 ms**。这是当前仍明显落后的路径。
- NGINX 的 256 并发普通代理第三轮 P99 达到 **6.772 ms**，同轮 rgnix 为 **6.454 ms**。不能宣称 NGINX 在每个窗口的尾延迟都更低。
- rgnix 的 64 并发 HTTPS 吞吐范围为 **56,628–81,876 请求/秒**，CV 为 **18.37%**。该波动未被解释，未删除任何窗口。

| 场景 | rgnix CPU | NGINX CPU | rgnix PSS | NGINX PSS |
| --- | ---: | ---: | ---: | ---: |
| 直接响应 | 8.15 | 2.90 | 34.82 | 20.39 |
| 静态文件 | 18.58 | 6.19 | 36.75 | 20.39 |
| 1 KiB HTTP 代理 | 20.99 | 8.52 | 36.33 | 20.94 |

普通代理的每请求 CPU 成本约为 NGINX 的 **2.46 倍**。在 256 并发下，该值为 **30.44 / 10.03 微秒**，PSS 为 **55.33 / 23.05 MiB**。因此差距也体现在 CPU 成本与内存占用上。本次没有做调用栈剖析，不能将差距归因到某个具体函数。

CPU 包括服务主进程及全部 worker 的用户态和内核态记账时间；rgnix 包括数据面、管理与后台线程。PSS 由 `/proc/PID/smaps_rollup` 每 200 ms 采样，并包含 NGINX master 和全部 worker。每个正式窗口启动新的前端，所以这里的 PSS 不应与旧报告跨场景连续运行的内存高水位直接比较，也不衡量长期内存增长。

## 配置、环境与可比边界

- OrbStack Ubuntu 25.10 / Linux `7.0.14-orbstack-00380-ga7e0a2dc9535` / aarch64。正式对照时间为 2026-09-27 **11:05:42–11:20:11 UTC**。共享 VM 与 macOS 宿主机，没有停止其他工作负载；CPU 绑定不等于独占物理核心。
- 前端均为 2 worker/线程，绑定 VM CPU 10,11；wrk 为 4 线程，CPU 2,3,4,5；共同的 OpenResty 上游为 4 worker，CPU 6,7,8,9。OpenResty 本轮仅用作上游，没有作为前端参赛。
- A/A 与正式对照分别通过 `unshare -n` 运行在临时网络命名空间，仅开启 loopback。两次命名空间退出后由内核回收；命名空间编号可能被复用。两轮的 `TCPSynRetrans`、`ListenDrops`、`ListenOverflows`、`TCPTimeWaitOverflow` 增量均为零，统计覆盖预热、预检和上游校准，不只正式窗口。
- HTTP/1.1 keepalive；访问日志、OTLP 导出、压缩关闭。NGINX 禁止代理请求/响应缓冲及自动重试，开启 sendfile。rgnix 保留内置指标、请求预算和 RGL 隔离限制；请求/插件并发预算分别为 4096/512。
- rgnix 使用当前默认的 **每 worker 128** 上游空闲池；NGINX 使用原对照配置的 **每 upstream、每 worker 512** keepalive。二者池容量并未完全对齐。64 个客户端连接低于双方预算；256 并发结果包含各自连接池行为，本次没有记录逐窗复用率，也没有单独测量池容量造成的差异。
- 请求头分流使用 NGINX 原生 `map` 与 RGL/Wasm，交替选择 primary/canary，并向上游设置 `x-selected`。路由与改写结果经过预检，但两者的执行模型和隔离成本不同，不是语言微基准。
- 上游响应和静态文件内容相同；文件位于 Linux 原生 `/tmp` tmpfs，属于热文件测试，不衡量磁盘吞吐。没有在计时路径读取 macOS 共享文件。
- HTTPS 仅在客户端到前端终止，上游仍为 HTTP。预检均协商 TLS 1.3 / TLS_AES_256_GCM_SHA384；未测握手峰值。
- 每个场景/并发组合交替启动双方，第二轮反转双方、场景及并发顺序。每窗启动全新前端，做语义预检，预热 3 秒，然后计时 8 秒。编译、功能回归和 profiler 不与压测重叠。
- 计时前的直接上游吞吐为 1 KiB 文件 561,244、16 KiB 文件 474,908、请求头上游 833,630 请求/秒。正式窗口中客户端最大 CPU 为 2.84/4 核，上游为 1.83/4 核；原始校准和进程采样均保留。

## 复现

使用上面摘要对应的二进制、现有 wrk/OpenSSL/Python/taskset，并保留脚本目录内依赖文件。输出目录必须不存在；根据机器调整互不重叠的 CPU 集合。

```bash
sudo unshare -n bash -c '
  ip link set lo up
  python3 scripts/benchmark_compare.py \
    --rgnix /path/to/round7/rgnix \
    --nginx /path/to/nginx/sbin/nginx \
    --openresty /path/to/openresty/bin/openresty \
    --engines rgnix nginx \
    --cases return static proxy-1k proxy-16k header tls \
    --server-cpus 10,11 --client-cpus 2,3,4,5 --origin-cpus 6,7,8,9 \
    --workers 2 --origin-workers 4 --client-threads 4 \
    --concurrency 64 256 --rounds 3 --seconds 8 --warmup 3 --interleave \
    --work-dir /tmp/rgnix-nginx-new --output /tmp/rgnix-nginx-new.json
'
```

A/A 使用另一个新目录，增加 `--candidate /path/to/round7/rgnix`，改用 `--engines rgnix candidate --cases proxy-1k`；其余参数一致。A/A 最大相邻差异按 `(max(pair) / min(pair) - 1) × 100%` 计算，CV 为样本标准差/均值。程序正常结束和零请求错误不代表通过稳定性门槛。

本次 Linux 原生目录为 `/tmp/rgnix-nginx-latest-20260927/`；配置、RGL/Lua 文件、每窗进程日志和未改写原始数据均保留。仓库 JSON 内也包含可重建的配置、脚本、命令及二进制身份。
