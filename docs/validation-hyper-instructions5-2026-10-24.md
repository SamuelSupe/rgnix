# Hyper 时钟、指标分片、路由与首部名复用（2026-10-24）

基线为 `b7c8858` 生产源码、`65a9cd7` 证据中的冻结 ELF。本轮保留启动时的指标
编号、直接路由位置、一次精确响应头时间戳，以及每连接有界首部名复用。
最终实现 `f7cd8b7`。最终数字以本文的完整程序配对为准；阶段收益不能相加。

[逐样本、逐函数、构建和回归证据](validation/hyper-instructions5-2026-10-24.json)。
本轮为本地提交，未合并 main 或推送 GitHub。

## 对所附分析的校正

1. 1% 是指令 A/A、CV 的重复性上限，并不是优化收益必须超过 1%。
   原生 CPU 成本另设 A/A、CV 5% 门槛；吞吐 10%、P99 20%。
2. 优化后分支已使用内联 H1 和分片指标，这些不重复实施。共享预算的 CAS、
   快照和后端租约仍存在；单 worker 指令不能评价其跨核一致性成本。
3. 本机循环中 Instant::now() 扣除空循环的中位数为 **11.88 ns**，七次约
   **11.49–14.59 ns**。这是两百万次紧密调用的净循环成本，不是应用中每次
   调用的边际延迟，不能从另一窗口的 vDSO 百分比推算 44 ns 或收益预算。
4. 再次实测 PMU：perf stat 退出 0 但 cycles/instructions 均为 not supported；
   perf c2c 退出 255，无 memory events。没有 IPC、HITM 或跨核争用的硬件结论。

## 保留的实现与代价

- 指标按全部监听地址的 H1/H2 worker 和 HTTP/3 运行时预留编号。宿主在任务
  启动前绑定 TLS；临时阻塞线程退出时归还编号，避免重建后进入其他服务范围。
  H3 的预留范围按配置并发给出保守上界；当前 background wrapper 默认单线程。
  不增加公开标签，scrape 仍同步合并全部累计 counter 和 histogram，保留 acquisition、
  全局和路由时长。更多内部分片会增加内存及抓取工作，没有声称降低 RSS。
- route matcher 返回所属快照的 host/route 位置，普通 H1 直接取得 prepared 下标，
  省去每请求 SipHash。公共 route API 与原调用者保持兼容；保留 Route Arc 和
  当前请求对快照的拥有关系，不让闲置下游连接长期钉住旧配置。
- 最终响应头就绪时读一次 Instant，同时用于 header 耗时和完整响应归池过期。
  header 耗时终点现在不包含后面的归池工作；流式 body 仍在实际完成时开始
  idle 期限。没有把 header 组装前的 upstream 起点和 checkout acquisition 起点
  混成一个时间；精确 deadline 和保活/首部定时器规则保持原样。
- HTTP/1 连接按字段位置缓存原始名称和已经验证的 HeaderName。只有当前原始
  名称字节完全相同时才复用名称；值、重复字段处理和帧长度继续由原 codec 解析。
  大小写或顺序变化照常解析。每连接最多 64 项，每项名字最多 64 字节，原始及
  canonical 名字载荷合计最多 8 KiB，另有最多 64 项描述符与 allocator 开销。
  64 次位置失配后清空、恢复整段原解析路径；有界 Vec 容量留到连接结束。
  上游与下游各自独立，因此连接很多时是明确的常驻内存交换。

没有采用 Box::leak Shared、批量扣留请求额度、让 active 连接持有 idle permit、
粗时钟或近似后端计数。这些会涉及生命周期、可用容量、闲置预算或诊断语义；
目前没有证据支持为节省原子写付出这些行为变更。

## 试验过程与不能外推的部分

最初不区分大小写的名称缓存相对 core 在 1 KiB / 宽首部多出约 1.94% / 0.66%
指令，交替名字多出 2.56%，因此撤销。改为精确字节比较并内联后，宽首部减少
8.90%，但交替名字仍多出 0.27%；随后把缓存/原始分支提升到整个 header block。
以上都是阶段对照，最终完整组合以上表为准。
宽首部的最终 flat self 中，HeaderName::from_bytes 约减少 9,459 指令/请求，
malloc、sdallocx 各减少约 1,953；缓存比较和引用计数又有新增成本。只能以完整
净减少约 9,540 为总体结果，不能把消失或内联重分配的符号逐项相加充当收益。

实验版最初漏掉 Pingora background_service() 暴露名称的 `BG ` 前缀，把所有
worker 编到 0。CPU 异常检查发现此缺陷，真实包装器的回归测试可捕获它。
这些测量保留为失败实现的证据，不能用来证明名称缓存、Route Arc 或时钟
某一项独立导致 CPU 回退。最终使用修正后的真实后台服务识别；同时恢复原
指标 TLS 热路径及 Route Arc 持有方式，避免保留没有独立证明的额外改动。

另有一次恢复 vendor 文件时保留了旧 mtime，Cargo 错误复用了上一份 ELF。
摘要比对在测量前发现；该构建标为 invalid，没有测量样本。后续刷新 mtime、
实际编译 Hyper/hyper-util/rgnix 后，使用新的不可变 ELF 路径。其失败记录保留。最终 16 KiB 对照的首次执行在 14 个完整记录后遇到
instrumented NGINX 优雅退出超时。失败目录和样本保留，整格在新目录重跑；
上表用完成的独立重跑，没有挑选或混合首次样本。

最终原生对照为双 worker、1 KiB、64 并发，数据线程固定到不同 guest CPU；
仍共享物理宿主。六回合交错，每窗口预热 8 秒、测量 5 秒，原基线、漏绑分片
的前版、最终修复版和 NGINX 共 **24 窗口，零错误**。事先声明的门槛不变。

不稳定。本轮只验收**可重复的指令减少及运行正确性**；缓存是否改善真实 CPU
和容量仍须独占环境确认。此前三个 CPU 试验的全部窗口和亲和性也保留在 JSON。

时钟调用栈的两次高频捕获分别有 268 和 1 个 lost chunk，不用于精确计数。
后续捕获无丢失；请求 period=16 的属性保留，但观察到的样本量不能证明
每十六次采一个，因此只解释调用者归属。精确总数采用独立无栈探针，包含

inline put、completion 与 runtime，不能把重叠语义范围相加作为独立成本。

独立 uprobe 在双 worker、单持久客户端上先预热 10 次，再校验 500 次响应。

也计入，静态改动合并一次读取，不能把全部差值当作完全确定的每请求次数。
最终时钟与分配探针均未观察到 lost 诊断。
