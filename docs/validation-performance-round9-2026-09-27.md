## 实现与行为边界

- HTTP/1 两个 HttpTask 通道改为父请求 future 内的固定容量队列，两侧借用，去掉通用队列和共享状态的独立 Arc 分配。每方向仍为 4 个槽位，读取 body 前仍先预留空间。取消释放预留并唤醒对端；互斥锁保证跨线程移动安全，没有新增 unsafe。成功异步收发保留 Tokio 协作预算，持续 ready 时仍让其他任务执行。
- 队列满的正常背压不再创建错误对象。头部临时偏移的前 16 项及响应小批次使用内联存储，更多头部仍动态扩展；原有公开 Vec 接口保留，HTTP/1 另加 iterator 写入入口。头部大小写、重复值、限制、过滤和报文顺序不变。
- 仅在 I/O 首次 Pending 时检查计时线程，去掉立即完成路径的 watchdog 时钟读取。使用 callback 已返回的 pinned timer，去掉重复装箱。业务指标精度、原超时粒度、Tokio fallback 和 watchdog 恢复不变。
- 生产依赖版本不升级：新增 `pingora-timeout` 0.9.0 的本地补丁，SmallVec 已在原 Cargo.lock 中。补丁语义与升级回归要求见 [vendor 说明](../vendor/README.md)。

## 固定成本的实测结果

Heaptrack：1 worker、4 个持久连接、2,000 个完整请求减去独立零请求启动对照。libc probes：一个预热连接、500 个完整请求。两类诊断与正式吞吐测试分开运行。下表累计申请字节不是 RSS；捕获复制仅含 libc memcpy/memmove，不含编译器内联或内核复制。

| --- | ---: | ---: | ---: | ---: |
| 2 B 直接响应 | 54.08 | 52.07 | 26,194 | 26,948 |
| 1 KiB 代理 | 101.19 | 89.65 | 108,594 | 105,042 |
| 16 KiB 静态文件 | 63.96 | 62.08 | 26,443 | 27,160 |

| 每请求 | 第八轮时钟调用 | 第九轮时钟调用 | 第八轮捕获复制 B | 第九轮捕获复制 B |
| --- | ---: | ---: | ---: | ---: |
| 2 B 直接响应 | 11.07 | 8.96 | 18,444 | 20,324 |

**取舍没有隐藏**：普通代理分配约减少 11.4%，但其捕获复制增加约 6.7%；直接响应累计申请字节增加约 2.9%。内联存储减少了独立分配，却扩大了部分临时状态。不能把分配次数下降等同于吞吐或内存占用同比改善。全部六个复制捕获窗口零丢样，解码事件数和记录数一致。

## 实际验证

- 640 项不同检查通过：应用/RGL 22、代理库 61、超时库 17、HTTP/1 协议 332、真实 HTTP 集成 94、产品功能 114。已有路由微基准保持 ignored，不计入通过数。
- 新队列测试覆盖有界交换、顺序、关闭、预留取消及其他任务能否运行。新增 HTTP 集成检查覆盖 40 个请求/响应头、重复 Set-Cookie 和 keepalive 请求隔离；原有流式请求、取消、上游断连不重放、TLS、HTTP/2、WebSocket、SSE、gRPC、热更新和排空检查通过。
- 补查中发现中间队列实现漏掉 Tokio 协作预算；删除预算的反向验证立即失败，补齐后代理库 61 项通过。中间候选的 12 窗功能组合对照出现过 198.603 ms 的直接响应 P99；另一次对照被主动中断。相关原始数据保留并明确排除出最终二进制结果。不能把预算修正视为该异常的已证实根因。
- 最终版本通过 release 构建、all-targets Clippy（拒绝 warning）和 208 项端到端检查；HTTP/1、计时器及应用未改源码的本轮测试结果沿用。vendor 测试使用隔离 workspace 的开发依赖锁，生产构建使用项目 Cargo.lock。Rust 格式和 diff 空白检查通过。
- 新增头部测试首次运行时误用了 HTTPConnection 不支持的 context manager，改成显式 finally 关闭后整套通过；这是测试脚本错误。
- **未运行**：真实 Kubernetes/Gateway 集群、amd64、完整 XDP、第三方 OTLP 平台、冷盘/网络文件系统、长期内存及容量验收。

## 环境、版本与复现

OrbStack Ubuntu 25.10 / Linux 7.0.14 / ARM64 / Rust 1.90.0，独立 network namespace。两个服务 workers 固定 CPU 10–11；wrk 四线程固定 CPU 2–5；共同 OpenResty 1.31.1.1 origin 的四 workers 固定 CPU 6–9。CPU affinity 不代表独占物理核。没有重启 OrbStack、修改 sysctl 或停止系统 NGINX（PID 494）。

明文 HTTP/1.1 keepalive，访问日志和 OTLP 输出关闭，保留正常指标、预算和安全检查。NGINX 1.30.5 关闭 proxy buffering、开启 sendfile；静态目录在 tmpfs，结果不代表冷盘或 HTTPS。NGINX 请求头分流用 map，rgnix 用 RGL/Wasm，两者的执行与隔离成本不同。本轮 OpenResty 只作为共同 origin，没有比较其前端。全部配置、命令、预检、CPU/PSS 和上游基线都在原始 JSON 中。
