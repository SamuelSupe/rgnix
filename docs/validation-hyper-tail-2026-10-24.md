# Hyper 1 KiB / 64 并发尾延迟分析与调度候选 — 2026-10-24

本轮将原生单线程服务 reactor 的外部事件检查间隔从默认 61 次任务轮询缩短为 16 次。三轮前后对照中，窗口 P99 中位观察值 **2.404 → 2.105 ms（−12.4%）**，三轮方向一致，P99 重复性门槛通过；吞吐中位观察值 **105,718 → 98,922 req/s（−6.4%）**，吞吐校准未通过。它是一项有吞吐取舍风险的本地候选，不能称为无代价提速，也不能把历史 9.526 ms 到今天的全部下降算作代码收益。

## 原先的高 P99 能归因到什么

旧 main `971afcd` 的六窗 P99 中位数为 9.526 ms，对应 Pingora 为 5.171 ms，但旧记录的吞吐和 P99 校准都失败。相同、未修改的 main ELF 在本轮无探针前后对照中的 P99 为 2.404 ms；另外一次带探针的短诊断为 0.782/0.971 ms。**同一 ELF 的历史高 P99 没有稳定重现，旧 84.2% 差距不足以判定实现回归。** 两个阶段的环境和窗口长度不同，不能相除当成优化收益。

旧窗口中 Hyper P50 通常更低，差异集中在尾部。两条数据线程的 CPU 用量接近，未见持续单 worker 空闲的明显迹象；约 715 万次 Hyper 上游获取中只有 2 次新建连接，其他均复用。源码确认上下游都已启用 TCP_NODELAY，HTTP/1 上游池也已按 worker 分开。本轮未以重建连接池或新增 TCP 参数作为修复。

新诊断的两份 Hyper 窗口均为零新建上游连接；两条数据 reactor 超过 5 ms 的唤醒样本分别为 0/0 和 1/1，reference 两窗均为零。服务端完成指标超过 5 ms 的样本分别为 19 和 0。该诊断启用了 1 ms 探针，不能混入正式性能结果。旧阶段没有保存同一时刻的完整延迟直方图和 reactor/reference 时序，故无法追溯每个旧尖峰的唯一原因；共享宿主调度、负载变化和延迟统计口径都是需要保留的解释，不能把旧尖峰全部归为这次修改的设置。

还核对了所用 wrk `debian/4.1.0-4build2` 的统计口径：它先执行停顿补偿，再把直方图交给 Lua `done()`，所以既有 P99 是补偿后的百分位，不是原始已完成请求的百分位，也不等于服务端请求处理耗时。[调用顺序](https://raw.githubusercontent.com/wg/wrk/4.1.0/src/wrk.c)、[校正算法](https://raw.githubusercontent.com/wg/wrk/4.1.0/src/stats.c)。一个明确标为合成的例子：100,000 个 0.3 ms 样本加 64 个 20 ms 样本，原始 P99 为 0.3 ms；按 1 秒、64 连接的相同算法补偿后为 10.415 ms。这说明该指标对短暂停顿敏感，不表示历史产品一定经历了此例中的暂停。正式对照继续保留相同口径。

## 针对性改动与机制验证

所用 Tokio 1.53.1 的默认设置在任务就绪队列持续忙碌时，每 61 次任务轮询检查外部 I/O 和定时器事件。单个任务的同步阻塞仍不能被此设置抢占。本轮只对单线程服务 runtime 设置 `event_interval(16)`，多线程服务的设置保持原值；心跳仍为默认 250 ms，诊断探针仍默认关闭。

用同版本 Tokio 做独立机制实验：一个 socket 读任务与 64 个持续自唤醒任务共处一个单线程 runtime，每个忙任务人为消耗 50 µs/次 poll。I/O 已就绪后的交付从 125 次任务轮询降至 80 次；每种设置交替运行 10 次，计数完全一致，交付时间中位数 6.281 → 4.030 ms。这是构造的就绪队列压力实验，不是 64 个真实代理连接的端到端收益，也不能据此宣称产品 P99 降低 36%。

## 产品前后对照

基线为 main `971afcde9389aa79e94b6947c5590382f796f655`，候选只修改 `src/runtime/host.rs` 的单线程 runtime 构造。430 个受测源码、锁文件和脚本摘要核对后，仅该源码文件不同。两份产物均为 OrbStack 原生 Linux arm64 / Rust 1.90.0 / LLVM 20.1.8，release、thin LTO、codegen-units=1、`http3,jemalloc`。

基线 SHA256：`28270d59d4f777d69ef2b2ae36df313399498b0c697ea02d48d4f4d0ec5f6734`；候选：`dfab37b67cddb8bca38598dafbc58e4831293a6c81fcaee2900afaa3c200ec36`。

三轮 P99 配对均值变化分别为 −1.7%、−28.3%、−12.9%；吞吐分别为 −3.6%、+6.0%、−2.4%。P50 观察值较高，P95/P99 较低，符合降低尾部排队时同时存在中段及吞吐取舍的可能；不能概括为所有延迟都改善。

门槛事先固定：每对 A/A 对称差 `200×|A−B|/(A+B)` 与六样本 CV，吞吐均须 ≤10%，P99 均须 ≤20%，且零错误。候选吞吐最差配对差 26.38%，故吞吐失败；P99 两边最差配对差为 10.16% / 17.65%，CV 也通过。通过重复性门槛不等于已获得生产收益置信区间，12.4% 仍是所测窗口的观察变化。

256 连接另外只做了两份样本/产物的筛查，吞吐中位观察变化 -0.14%，P99 -14.26%。基线两窗差异较大，且不满三对样本；这只能排查明显问题，不能证明高并发容量没有回退。

## 原始延迟与补偿口径复核

另外用系统原有 wrk 的 Lua `done()` 导出完整补偿直方图，没有增加逐请求回调。依据已核对的算法反解原始直方图，并要求每窗：原始样本数等于完成请求数、重新正向补偿逐 bin 完全一致、补偿 P99 与正式输出一致。固定边界向量的反解自检也通过。它是事后直方图重建，不是逐请求时序追踪；只有每产物两窗，属于诊断，未达到三对的性能资格。

| 产物 | req/s | 重建原始 P99 ms | wrk 补偿 P99 ms | 原始 / 补偿样本数 |
|---|---:|---:|---:|---:|
| main Hyper | 101,545 | 1.556 | 2.274 | 1,524,392 / 1,578,141 |
| event16 Hyper | 104,289 | 1.345 | 1.861 | 1,574,724 / 1,615,197 |
| event16 Hyper | 125,444 | 1.249 | 1.692 | 1,894,102 / 1,962,687 |
| main Hyper | 116,324 | 1.276 | 1.867 | 1,756,431 / 1,811,996 |

重建原始 P99 的两窗中位观察值为 1.416 → 1.297 ms（-8.4%），与补偿 P99 方向相同，但两份样本不足以确认稳定收益。原始与补偿后的值都保留；不会将改用原始 P99 作为优化收益，也不会将服务端完成直方图与客户端 P99 直接相减归因某个阶段。

## 验证和复查

候选在 OrbStack 通过 522 项运行检查：Hyper 基础集成 105、双 worker 与临时监听端口专项 69、产品策略 115、含 HTTP/3 的协议检查 71、Ingress 恢复 57、Pingora 基础集成 105。release 库测试 27 通过、1 忽略；格式及 `cargo clippy --release --locked --features http3,jemalloc --all-targets -j4 -- -D warnings` 通过。覆盖重载快照、预算、取消、超时、不重放、连接复用、H2/H3、WebSocket 与排空。
