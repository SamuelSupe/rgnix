# 第六轮性能优化：后端选择并发与连接池复用（2026-09-27）

基线为[第五轮](validation-performance-round5-2026-09-27.md)最终二进制。本轮生产变更集中在 `src/backend.rs` 与 `src/runtime.rs`。源码尚未提交或发布，v0.4.0 下载和镜像不包含这些改动。

## 最终默认配置的结果

最终二进制为 `b0ab0508…`，默认上游空闲池预算保持每 worker 128。[最终 A/B 原始记录](validation/performance-round6-default-http-2026-09-27.json)，双 worker、64 并发、三轮中位数：

| 场景 | 吞吐 req/s：旧 → 新 | 吞吐变化 | CPU µs/请求：旧 → 新 | P99 ms：旧 → 新 |
| --- | ---: | ---: | ---: | ---: |
| 单后端普通代理 | 107,240 → 108,292 | +1.0% | 18.49 → 18.22 | 1.403 → 1.553 |
| 64 后端 header 哈希 | 46,725 → 62,999 | **+34.8%** | 35.60 → 31.36 | 3.850 → 2.480 |
| 256 后端 header 哈希 | 21,837 → 30,908 | **+41.5%** | 63.56 → 64.03 | 10.189 → 3.918 |

64 后端的 CPU/请求下降 **11.9%**。256 后端 CPU/请求约持平（+0.7%），吞吐主要来自多个 worker 能同时评分；不把并行度提升当作同等 CPU 节省。普通单后端的吞吐差异小于 A/A 波动，没有确认提升。

普通代理 P99 中位数仍高 **0.150 ms**，本轮不认定普通代理尾延迟改善；A/A 中同一最终二进制的普通代理 P99 范围为 1.367–2.420 ms。256 后端旧版 P99 三窗为 11.144 / 10.189 / 6.769 ms，全部保留，不删除旧版较慢窗口。哈希收益仅适用于本次端点数、键分布及双 worker 场景。

[最终默认版本 A/A](validation/performance-round6-default-aa-2026-09-27.json)覆盖普通单后端和 256 后端哈希：最大成对吞吐差异 **7.06%**、最大组内 CV **8.41%**，通过既有 10% 吞吐波动门槛。该门槛不验收尾延迟或长期容量。

最终默认版本 A/A 与 A/B 合计 **30 个窗口、15,566,722 次请求，错误和 SYN 重传均为 0**，另有 1,920 次前置目标地址与完整响应体检查。预热、上游直连、中间候选和失败实验不计入这个数字。较大的连接池没有作为默认收益的一部分。

## 扩大连接池的候选：保留为显式调优

下表是默认池预算为 1,024 的**中间候选**（`38b8f28…`），相对第五轮的[隔离网络 A/B](validation/performance-round6-http-2026-09-27.json)。最终源码恢复默认 128，以下数字不冒充最终默认版本结果。双 worker、64 并发，三轮中位数：

| 场景 | 吞吐 req/s：旧 → 新 | 变化 | CPU µs/请求：旧 → 新 | P99 ms：旧 → 新 |
| --- | ---: | ---: | ---: | ---: |
| 单后端普通代理 | 106,082 → 105,552 | −0.5% | 18.75 → 18.77 | 1.219 → 1.522 |
| 64 后端加权轮询 | 79,803 → 98,664 | **+23.6%** | 24.85 → 19.88 | 1.703 → 1.939 |
| 64 后端 header 哈希 | 46,503 → 61,575 | **+32.4%** | 36.00 → 32.14 | 4.007 → 2.372 |
| 256 后端 header 哈希 | 20,643 → 29,590 | **+43.3%** | 65.52 → 66.88 | 7.546 → 4.554 |

普通单后端吞吐和 CPU 基本持平。64 后端轮询的 CPU/请求下降 **20.0%**，64 后端哈希下降 **10.7%**。256 后端哈希的 CPU/请求没有下降（中位数高约 2.1%）；它主要通过允许多个 worker 同时评分提高 CPU 利用率和吞吐，不能把 43.3% 吞吐增长解释成同等 CPU 节省。

64 后端轮询三窗的上游新建连接占比从 **25.38% → 0%**（正式窗口、已预热），直接验证复用改善；新旧版本在这些隔离窗口中都没有 SYN 重传。此项峰值 PSS 的三窗中位数从 **30,809 → 31,064 KiB**，没有测满空闲池或大量 TLS 连接的最坏内存占用。

主矩阵的普通代理和轮询 P99 中位数分别上升约 **0.303 / 0.236 ms**，独立专项复测见下表。全部主矩阵窗口均保留，复测不替换主表数据。

[轮询尾延迟专项](validation/performance-round6-pool-tail-2026-09-27.json)使用新网络命名空间和相同候选，各窗延长到 12 秒、三轮交替：

| 场景 | 吞吐 req/s：旧 → 新 | CPU µs/请求：旧 → 新 | P99 ms：旧 → 新 |
| --- | ---: | ---: | ---: |
| 单后端普通代理 | 109,617 → 109,060 | 17.89 → 18.12 | 1.590 → 1.437 |
| 64 后端轮询 | 84,021 → 98,566 | 23.56 → 19.70 | 1.921 → 2.570 |

单后端 P99 回升没有稳定复现。多后端轮询的 P99 中位数在两批对照中均更高，专项新版三个窗口为 **3.028 / 1.820 / 2.570 ms**。因此**撤回默认预算升至 1,024 的调整**，保留为需要显式传参的吞吐/资源/尾延迟取舍；没有继续把它计为无回退的默认优化。

[扩大连接池候选的 A/A 校准](validation/performance-round6-aa-two-workers-2026-09-27.json)覆盖单后端代理、64 后端轮询和 256 后端哈希，18 窗：最大成对吞吐差异 **6.76%**、最大组内 CV **5.90%**，通过二者均不超过 10% 且无错误的既有门槛。这是吞吐波动门槛，不是 P99 门槛；A/A 的 256 后端哈希仍出现 **5.036 ms P99**。

该候选的 A/A、正式 A/B 和尾延迟专项合计 **54 窗、39,047,710 请求，错误和 SYN 重传均为 0**。计数不包括预热、上游直连、前置验证、失败的原网络实验和单轮初筛。每窗 64 次前置检查还验证了实际目标地址及完整响应体。上游直连约 58–65 万 req/s，有余量。

这些是双 worker 场景的短时对照；没有重测本轮单 worker、多节点和持续生产负载的吞吐，不是全产品容量承诺。

## 实现与资源边界

- 多端点 Hash/Sticky 选择只在持有后端池锁时取得一份不可变端点列表，随后释放锁并计算评分，允许不同 worker 同时执行。加权哈希公式、键和端点顺序保持不变。
- 普通轮询、最少连接及单端点选择继续沿用原来的互斥范围，避免给普通代理增加读写锁成本，也保留最少连接选择和占用计数的串行更新。
- 并发额度用原子比较更新领取，避免并行哈希选择越过后端 `max_inflight`。每个 Lease 仍持有自己的端点状态，释放时归还额度。
- DNS 发布新端点列表后，新选择读取新列表；已经开始的选择可以在旧列表上完成。旧 Lease 的失败计数不会污染新地址的健康状态。淘汰列表的最后一个引用可能在请求线程释放；本轮没有测量大规模 DNS 频繁更新时的释放成本。
- 上游空闲池默认预算保持每 worker **128**。增加 `--upstream-keepalive-pool-size` 供显式调优，允许 **1–65,536**，适用于 serve/ingress/gateway，调整需要重启。

连接池实际容量为每个监听服务、每个 HTTP/1 或 HTTP/2 空闲池的 `threads × upstream_keepalive_pool_size`；各后端共享该容量。连接按流量建立，不预先创建；这是空闲连接预算，不是总连接或请求并发上限。较大容量会保留更多文件描述符、TLS 状态及内存。显式设置 1,024 可尝试减少端点较多时的连接淘汰，但需验收上面的尾延迟取舍。

Helm 提供可选 `upstreamKeepalivePoolSize`；默认不传新参数，以兼容 Chart 当前默认的已发布 v0.4.0 镜像。仅为包含新参数的源码构建镜像设置此值。[部署说明](deployment.md#资源与上游故障保护)给出了计量方式和调整边界。

## 诊断过程和未关闭的问题

首次使用 RwLock 的候选在单轮初筛中令单后端普通代理吞吐下降约 12.5%，已撤回。[原始记录](validation/performance-round6-rwlock-rejected-2026-09-27.json)保留全部八窗；没有把这次单轮结果当成稳定性能结论。最终实现保留 Mutex，只缩短 Hash/Sticky 的持锁范围。

随后在原 Ubuntu 网络命名空间中的[首次 A/A](validation/performance-round6-aa-shared-network-failed-2026-09-27.json)失败：最大成对差异 **39.70%**、最大组内 CV **13.05%**，出现 **65.526 ms P99**。[首次 A/B](validation/performance-round6-http-shared-network-interrupted-2026-09-27.json)在第 20 个窗口因超时中止，末窗仅完成 132 请求，吞吐 16.29 req/s。上述数据保留，没有混入后续正常窗口中计算收益。

[线程及连接诊断](validation/performance-round6-stall-diagnostic-2026-09-27.json)显示停顿时数据面线程等待网络，连接处于 SYN-SENT 并反复重传。上一轮基线也复现停顿，45 秒仅完成 538 请求；即使 wrk 错误数为零，也不能据此认为窗口健康。诊断包含 debugger 暂停，不作为吞吐基准。

[网络诊断](validation/performance-round6-network-diagnostic-2026-09-27.json)进一步记录：

- 基线 64 后端轮询完成约 152 万请求期间，系统累计约 38.3 万次新建连接，TIME_WAIT 达到 65,536 附近；这暴露了原空闲池频繁淘汰连接的问题。
- 停顿时绕过 rgnix，直接访问 NGINX 后端的两批 64 地址探测也分别有 **45 / 38** 次超时；监听队列没有积压，NGINX 错误日志为空。
- TCP SYN 重传增加 **531** 次，TIME_WAIT 溢出增加约 **29.4 万**次。它们发生在同一诊断中，但尚未证明 TIME_WAIT 溢出就是 SYN 停顿的内核原因。

后续压测将客户端、代理和上游一起放进临时 Linux 网络命名空间，仅启用该命名空间的 loopback；不修改原网络、系统 TCP 参数或其他工作负载。它隔离网络状态，仍共享 OrbStack VM 的 CPU 和内存。原命名空间的 SYN 停顿原因仍未完全解释，不能认定产品所有网络停顿或此前尾延迟问题已解决。

## 测试环境与复现

- OrbStack Ubuntu / Linux 7.0.14 / aarch64，Rust 1.90.0；release、thin LTO、单 codegen unit，锁定依赖未改动。
- HTTP/1.1 keepalive，64 并发，完整 1 KiB 响应体，64 个 32 字节键轮换；端点权重按 1–5 循环。
- 每窗启动新代理进程，预热 3 秒、正式 8 秒；三轮交替新旧版本顺序。每窗另外检查 64 个请求的状态、完整响应体，以及旧公式或轮询顺序推导的实际后端。
- 代理双 worker 固定 VM CPU 10,11，wrk 两线程固定 2,3，NGINX 1.30.5 上游两 worker 固定 6,7。编译、回归测试及调试器不与正式压测并行。
- 不同端点使用不同 loopback 地址，共享一个 NGINX 上游进程，不是独立 Pod。没有重做 NGINX/OpenResty **前端**对比；这些结果不能证明整体超过它们。
- 访问日志及 OTLP 导出关闭，rgnix 正常代理流程和指标仍启用。每窗读取建连/复用计数与 TCP 计数器，指标读取在计时窗口之外。
