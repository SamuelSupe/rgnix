# rgnix 数据面性能优化 — 2026-09-27

后续工作见[第二轮优化记录](validation-performance-round2-2026-09-27.md)：分配进一步减少，但测量波动、吞吐及尾延迟回退尚未满足整体性能发布门槛。本文保留第一轮历史结果。

**本轮显著缩小了差距，仍未追平 NGINX/OpenResty。** 在 64 并发、三轮中位数下，1 KiB HTTP 代理从 **50,504 → 81,989 req/s（+62.3%）**，16 KiB 静态文件 **+118.2%**，请求头 RGL 分流 **+104.4%**。相应每请求 CPU 成本分别下降 **33.9% / 48.7% / 44.4%**。混合负载的进程 PSS 观测峰值从 **159.0 → 119.0 MiB**。

最终矩阵完成 **162 个窗口、143,213,435 次请求，状态、连接、读、写和超时错误计数均为零**。13/14 个优化前后场景/并发组合中，优化版三轮最低吞吐高于基线最高吞吐。64 并发直接响应未证明稳定提速，其 P99 中位数还有小幅回升；高并发 POST 有一个 **85.923 ms** 的尾延迟异常，定向复测未重现，原因尚未确定。不能据此宣称所有尾延迟问题已经解决。

这是 **v0.4.0 之后的未发布源码优化**。GitHub v0.4.0 下载和镜像仍是旧版；[上一次发布版对比](validation-nginx-openresty-2026-09-27.md)的数据没有被改写。此次优化前后都从同一基线、同一锁定依赖和编译参数原生构建，避免把编译环境变化当作代码收益。

## 改动及依据

[CPU 采样](validation/performance-profile-2026-09-27.json)覆盖普通代理、静态文件、请求头脚本的优化前后版本，使用 `perf cpu-clock`、199 Hz、11 秒采样和 DWARF 调用栈；没有丢失样本。采样与正式压测分开。基线的唤醒、时间读取和分配开销显著；优化后这些仍是热点，不能把各符号的样本比例直接解释成绝对每请求收益。VM 不支持本次所需的硬件 cycles/instructions 计数。

- **运行时与连接复用**：使用固定 worker 的运行时，减少任务迁移；上游池按 worker 和原有 TLS 策略分组，idle 检测在释放连接的当前运行时执行。CA、ALPN、客户端身份隔离和 idle 检查保留。接受循环绑定到创建监听 socket 的运行时，错误路径主动让出执行权，修复立即退出时的错误循环。
- **静态文件**：用共享路由引用代替深拷贝 Settings/MIME 表；复用已读取的文件元数据。普通 GET 的文件不超过 64 KiB 时，在同一个阻塞任务中打开并读取；大文件、Range、条件请求保留流式处理。移除无效的 seek(0)，将读取缓冲直接移交给 Bytes。没有增加文件内容缓存，文件更新、根目录约束、特殊文件防护、GET/HEAD/Range/304 行为保留。
- **阻塞任务预算**：每个固定 worker 的阻塞线程上限为 `max(1, min(2, 16 / threads))`；每个监听服务默认两个 worker，合计最多四个阻塞线程，多个监听服务分别拥有运行时。固定 worker 后不能简单保留每池 16 的配置，否则线程池数量会放大；较小的池避免热文件任务挤压 socket 调度。管理和后台服务另有运行时，`--threads` 不是整个进程的总线程数。冷文件存储的排队表现需要单独验证，见[部署说明](deployment.md)。
- **RGL**：Wasm 仅导入实际使用的宿主函数，重映射函数索引；宿主调用使用有类型的 trampoline，省去每次调用的参数向量分配。只有请求钩子的脚本在成功后立即释放 Store、实例和额度；有响应钩子的脚本继续保留请求状态。旧 `.wasm` ABI 仍可加载，每请求隔离、fuel、8 MiB Wasm 内存和 1 MiB 宿主预算保留。
- **请求与指标**：去掉重复请求字段/头部构造和无配置限流器的锁、时钟操作；健康端点没有 backoff 时避免读取时钟。指标标签命中走读锁并借用已有字符串，2048 个标签的总预算和溢出指标仍生效。指标没有从生产路径移除。
- **请求正文**：仅在确有重试预算时启用 Pingora 自动重试缓冲；rgnix 仍只有一次上游尝试。显式正文预读的回放缓冲继续保留，已读取字节仍完整转发一次。

## 没有掩盖的回退与修正

第一版固定 worker 优化虽然吞吐提升，但 256 并发静态文件的两次 P99 为 **37.465 / 34.327 ms**。这不是可接受的结果；剩余矩阵被中止，已完成的 **73 个窗口全部保留**于[被淘汰候选记录](validation/performance-static-tail-rejected-2026-09-27.json)，没有挑选其中较快的窗口放进最终结果。

把原先每服务 16 个阻塞线程简单分摊为每 worker 8 个，P99 仍为 **5.949 / 21.684 / 23.807 ms**，因此[该候选](validation/performance-pool-eight-rejected-2026-09-27.json)也被淘汰。最终将每 worker 限到两个阻塞线程；[重新交替测量的静态专项](validation/performance-pool-two-2026-09-27.json)中，256 并发吞吐中位数从 **32,756 → 101,998 req/s**，P99 从 **13.449 → 10.986 ms**。最终候选的该专项仍有 **14.631 ms** 的单轮 P99，未删除；后续重新执行本文完整矩阵，不把专项样本加入主表。

功能回归也曾发现新运行时的 SIGINT 退出挂起：监听 socket 的 reactor 和 accept 循环不在同一运行时，退出时反复立即报错且不让出执行权。修正运行时归属及错误路径后，重新跑完全部回归，并完成最终二进制的 100 次启动、实际 OTLP 401 请求/丢弃、SIGINT 停止循环；保留原先 15 秒停止期限，没有通过放宽断言掩盖失败。

## 环境与复现

- OrbStack 2.2.3 的 Ubuntu 25.10，Linux `7.0.14-orbstack-00380-ga7e0a2dc9535`、aarch64。宿主 Mac17,7，18 个逻辑 CPU、64 GiB RAM；还有其他 VM/工作负载，未独占物理主机。
- 源码、文件和运行目录在 Linux 原生 `/tmp` tmpfs，计时期间不从 macOS 共享目录读取文件。这是热文件测试，不能代表物理磁盘、NFS 或对象存储。
- 前端两 worker，VM CPU `10,11`；wrk 四线程，CPU `2,3,4,5`；统一 OpenResty 上游四 worker，CPU `6,7,8,9`。CPU 集合不重叠，但不代表独占物理核心。
- 每场景预热 1 秒，测量 6 秒，64/256 并发，三轮；轮换引擎顺序，第二轮反转场景/并发顺序。构建、回归和插桩采样均在正式测量之外完成。
- wrk `4.1.0-4build2`，HTTP/1.1 keepalive、loopback。HTTPS 仅客户端到前端使用 TLS，前端到上游为 HTTP；预检验证 TLS 1.3 和相同测试证书。未测 HTTP/2 吞吐、握手洪峰或上游 TLS 容量。
- 全部关闭访问日志、OTLP 输出、压缩、配置的鉴权/限流和上游重试；rgnix 的正常指标、请求/插件预算及沙箱继续工作。请求预算 4096、插件实例预算 512，用于容纳 256 并发；不是产品默认容量。NGINX/OpenResty 开启 sendfile、上游 keepalive，关闭代理请求/响应缓冲。
- 每次启动做正文、状态、分流后端、请求头和 TLS 预检；POST 校验完整长度和 MD5。wrk 每个测量窗口单独保留状态、连接、读、写、超时错误计数。

两个 rgnix 二进制 CLI 都仍显示 0.4.0，须用摘要区分。此前 GitHub release 的二进制不是此次同工具链重建的优化前样本。生产 patch 摘要通过 `git diff -- src vendor/pingora-core/src/connectors/mod.rs vendor/pingora-core/src/services/listening.rs vendor/pingora-proxy/src/proxy_h1.rs vendor/pingora-proxy/src/proxy_h2.rs` 计算；回归 JSON 还记录了每个变更构建文件的 SHA-256。

```sh
python3 scripts/benchmark_compare.py \
  --rgnix ./rgnix-before --candidate ./rgnix-after \
  --nginx /path/to/nginx --openresty /path/to/openresty \
  --engines rgnix candidate nginx openresty \
  --work-dir /tmp/rgnix-comparison-new --output ./comparison.json \
```

这些是共享虚拟机上的短时闭环结果，不能给出固定到达速率下的 SLO、长期内存稳定性、生产 Kubernetes/CNI、物理 NIC 或冷文件存储容量保证。剩余工作应继续由采样和相同条件对照驱动，重点检查事件/唤醒路径和每请求分配，而不是用关闭安全与观测能力来提高数字。
