# Hyper 接收缓冲区与请求 future 优化（2026-10-01）

本轮保留实验性 Hyper 的空闲上游接收探测优化，累计申请字节减少约 44%，捕获复制开销基本不变。新增的去装箱请求 API 没有取得一致收益，已经撤下。默认 Pingora、既有 worker 归属、共享预算、超时和不重放请求规则保留；源码和证据在本地，未提交、推送或发布。

## 实现与取舍

- 空闲上游连接只需区分 Pending、EOF 和异常数据。原路径会先为读取预留整块缓冲区；当上一响应仍持有该分配时，即使 socket 没有数据也会触发新的分配。现在使用一个字节的临时缓冲区进行空闲探测；收到异常字节时保留它，继续拒绝该连接。活动响应、流式消息和服务器读取继续使用原读取策略。改动仅随 `rgnix-reuse-buffer` 启用。

曾尝试让普通代理借用客户端、直接返回具体类型的 request future，省去一次装箱和客户端克隆。首版额外 async 包装使复制开销增加约 20%；直接返回发送 future 后，复制仍增加约 6%。后续完整吞吐对照没有提供一致收益，最终恢复原请求接口。这个 API 没有保留在产品代码中，试验补丁和各阶段计数已归档。

独立 `--owned-http1` 原型还修复了上游截断的处理顺序：连接 driver 可以在报告 EOF 前已经交付响应头或 body frame，现在先交付已就绪的响应数据，再报告错误。这个原型没有接入产品内核。初次验证失败后中止了原型性能测试，仅产生两个 legacy 窗口，没有 owned 性能窗口；不能用它得出性能结论。

## 分配与复制计数

OrbStack Ubuntu / ARM64，双 worker，一个持久客户端连接，10 次预热后 500 次请求，每次校验 200 和完整 1 KiB body。分配使用 prefixed jemalloc 入口 uprobes，排除内部嵌套调用；复制只捕获 libc memcpy/memmove，不包含内联复制。计数包含后台操作，不是吞吐、延迟或存活内存。

| 候选 | 分配/重分配调用每请求 | 累计申请字节每请求 | 捕获复制字节每请求 |
|---|---:|---:|---:|
| 旧版 worker 方案 | 16.526 | 4,694.232 | 5,923.088 |
| 首版去装箱，仅请求 API | 15.592 | 3,331.368 | 7,137.760 |
| 首版去装箱 + 空闲探测 | 15.096 | 1,289.832 | 7,134.000 |
| 已撤下：直接返回 future + 空闲探测 | 15.052 | 1,286.408 | 6,276.000 |
| 保留：仅空闲探测 | 16.026 | 2,636.232 | 5,919.872 |

保留方案累计申请字节减少约 **43.8%**，调用减少约 **3.0%**；捕获复制字节基本不变（-0.05%）。500 次测量中的 8 KiB 分配从 131 次降到 6 次。时钟调用仍约 20 次/请求，没有在本轮优化。各阶段原始计数分别保存在 `validation/hyper-dispatch-{alloc,primitives}-{before,inline,optimized,direct,idle}-2026-10-01.json`。

## 产品性能对照

同一 OrbStack Linux ARM64、Rust 1.90、jemalloc 构建，NGINX 1.28.0。双 worker、4 个源站 worker、4 个压测线程；frontend / client / origin 的虚拟 CPU 集合分别为 10–11 / 2–5 / 6–9。每窗预热 3 秒、测量 12 秒，三轮，每程序每轮两次重复窗口，顺序轮换。仅比较无 TLS、无插件、关闭访问日志的普通 1 KiB HTTP/1 代理；上游重放与缓冲均关闭。

最终 **36 窗、65,322,867 请求、零错误**。源站直连约 506,795 req/s。下列吞吐及 CPU 为窗口中位数，P99 和 PSS 为窗口最大值：

| 64 | 旧版 | 141,845 | 13.98 | 5.583 | 30.51 | 未通过 |
| 64 | 保留方案 | 139,918 | 14.22 | 3.072 | 30.43 | 未通过 |
| 64 | NGINX | 215,311 | 9.24 | 2.608 | 20.31 | 未通过 |

观测吞吐变化为 **-1.36% / +3.92%**，CPU 成本变化为 **+1.75% / -3.39%**。观测候选吞吐约为 NGINX 的 65% / 69%，仍有差距；这不是稳定比值、性能对等或生产容量结论。旧版和候选都有超过 10% 的重复窗口差异；NGINX 的相邻重复窗口较接近，但跨轮变异仍为约 12%–19%。按照每组重复差异和跨轮变异均不超过 10% 的既有门槛，**所有组失败**，不能确认稳定吞吐收益。降低累计分配量没有在本轮证实能够显著缩小吞吐差距。

保留空闲探测方案的依据是可复现的分配下降与相同的活动读取路径；没有引入新的请求接口或更大的异步状态。测试受共享虚拟机与宿主环境波动影响，专用环境的比较尚未完成。[最终原始窗口](validation/hyper-dispatch-idle-1k-2026-10-01.json)、[校准分析](validation/hyper-dispatch-idle-1k-analysis-2026-10-01.json)。

去装箱组合试验完成了 36 个窗口、56,451,520 请求、零错误。64 并发的旧版 / 候选 / NGINX 中位数分别为 119,857 / 114,269 / 178,346 req/s；256 并发分别为 117,296 / 87,125 / 144,781。观测 CPU 成本也较高。所有组都未通过完整 A/A 校准，无法把下降的具体幅度归因给代码；但分配更少、复制更多且缺少一致收益，不足以支持保留额外接口。这个组合已经撤下，不能拿它代表当前代码。详见[撤下候选原始窗口](validation/hyper-dispatch-product-1k-2026-10-01.json)、[校准分析](validation/hyper-dispatch-product-1k-analysis-2026-10-01.json)与[试验补丁](validation/hyper-dispatch-request-future-trial-2026-10-01.patch)。

## 实际验证与边界

最终 native 候选在 OrbStack 上通过双 worker 生命周期 **57** 项、综合集成 **99** 项、产品功能 **115** 项，共 **271** 项运行检查。覆盖流式上传、取消、不重放、WebSocket、HTTP/2、重载、TLS/mTLS、认证、插件和遥测。两个已撤下的请求 API 候选也通过相同检查；这些通过记录分别保存，未混算为当前版本的验收。

内核连接边界 **12** 项通过，新增检查覆盖立即或稍后到达的异常空闲数据。客户端及连接池 **58** 项通过（另外两项按原测试设置跳过），涵盖 EOF、异常 body、连接复用、丢弃响应、升级和 HTTP/2。独立原型在双 local worker 下，legacy 和 owned 模式各 **10** 项通过。

最终格式检查、Hyper + jemalloc 全目标 Clippy、独立原型 Clippy、默认构建检查通过；Hyper 的 server-only + reuse-buffer 组合也通过编译检查。这些静态检查单独记录，不算运行验收。

本轮没有验证 amd64、非 Linux、TLS/H2/RGL/静态文件吞吐、长时间稳定性或多副本 Kubernetes 容量。此前 mTLS CA 轮换后的偶发 reset 仍未解释，本轮产品验收通过不能说明它已修复。

机器记录保存在 [hyper-dispatch-2026-10-01.json](validation/hyper-dispatch-2026-10-01.json)，包含二进制摘要、最终相关源码摘要、命令、计数工具及验收日志。补丁基于本轮开始时捕获的脏工作区，不是相对干净 HEAD 的补丁。
