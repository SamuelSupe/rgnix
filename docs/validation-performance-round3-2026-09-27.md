# 第三轮数据面性能优化 — 2026-09-27

**本轮确认进一步减少了分配调用；尚未证明整体吞吐提升，也没有完成性能发布验收。** 相对第二轮优化版，普通代理、静态文件、请求头 RGL 分流分别减少约 **11.0% / 14.0% / 7.6%** 的分配调用。最终候选通过 **395 项 Rust / 原生行为检查**。改动仅在当前源码，未提交或发布。

两个 A/A 控制实验都没有通过预先设定的稳定门槛。下文的新旧版本及 NGINX 对照是诊断记录，不能把它们的中位数变化直接解释为代码造成的收益或回退。上一轮记录见[第二轮报告](validation-performance-round2-2026-09-27.md)。

## 改动及兼容边界

- 请求头使用保留原始 `HeaderMap` 的只读视图，按需读取；认证修改时才生成字符串映射。独立模式继续读取重复字段中最后一个有效 UTF-8 值；Gateway 保留既有的首值投影。原始重复字段及无效 UTF-8 字节仍计入 RGL 宿主数据预算。
- Gateway 超时计算与请求处理复用同一份请求字段和匹配结果，不重复构建头部映射、规范化路径和匹配路由；每个请求仍持有同一份不可变配置快照。
- 普通代理没有 URI / query / 路径修改时，复用已经解析的原始 URI；绝对形式 URI、`proxy_pass` URI 替换和脚本改写仍执行原来的转换。变量展开尽量借用字符串。
- 单端点选择跳过临时候选向量和权重求和。没有主动健康检查且没有被动失败时跳过健康锁；成功请求直接通过已持有的端点 lease 记账。后端并发上限仍在池锁内检查，失效、冷却及恢复规则保留；旧 DNS 地址上的在途请求失败不会影响替换后的端点。
- 路由计数、状态计数和直方图缓存 Prometheus 句柄，避免每请求重复解析标签及查找计数器。保留原有指标、全局 2,048 个动态标签预算和溢出计数；没有通过删除指标、采样指标或放宽沙箱换取结果。

新增回归针对重复 / 非 UTF-8 请求头变量、单端点被动摘除与冷却恢复，并在现有 DNS 端点替换测试中检查旧 lease 的失败归属。认证身份头替换、并发预算、URI 语义、热更新、HTTP/2、TLS、WebSocket、正文流式及插件限制由现有行为套件集中覆盖。

新增 `examples/minimal_proxy.rs` 仅作同版本 Pingora 传输基线：没有产品路由、安全策略、预算或指标，**不是可部署的产品运行模式**。基准脚本增加该引擎、各线程 CPU 时间和最后运行的 CPU；实测发现的随机端口重复分配已修复。

## CPU 热点诊断

[采样原始记录](validation/performance-round3-profile-2026-09-27.json)在全部正式压测结束后单独采集：1 KiB 代理、64 并发、两个 worker、`cpu-clock` 199 Hz、11 秒、DWARF 调用栈。rgnix / 最小 Pingora / NGINX 分别得到 4,356 / 4,215 / 4,310 个样本，均无丢失样本；NGINX 包含 master 和两个 worker。

| 符号 | rgnix 样本比例 | 最小 Pingora | NGINX |
| --- | ---: | ---: | ---: |
| `__wake_up_sync_key` | 12.90% | 14.19% | 17.33% |
| `__kernel_clock_gettime` | 5.74% | 2.33% | 未列出 |
| `malloc` | 1.45% | 1.49% | 未列出 |
| `cfree` | 2.41% | 2.16% | 未列出 |

表格只保留占比至少 0.5% 的符号；“未列出”不代表没有成本。采样比例不能跨引擎直接当作每请求耗时，也不能与另一轮未插桩吞吐相乘。采样器输出的 `Woken up` 是 perf 自身唤醒次数，不是代理唤醒次数；候选采样中该值明显高于另两组，因此这些单窗口样本仅用于查找候选热点。

后续值得验证的是连接与 worker 的归属、计时器及重复读时钟开销。当前证据尚不能证明跨 worker 唤醒是唯一根因，也不能保证调整 listener / reactor 就能缩小差距；本轮没有再次引入上一轮被撤回的 reactor 迁移。

Ingress 恢复使用模拟 Kubernetes API，不能替代实际集群验收。[本轮集群尝试记录](validation/performance-round3-gateway-blocked-2026-09-27.json)：在 OrbStack v1.35.6+orb1 新建专用 Gateway 验证命名空间，但第一项 Service 创建即报 `failed to allocate a serviceIP: range is full`，没有进入 Gateway 主流程。两个新建测试命名空间已清理；没有在未获确认时删除已有 QA 工作负载。本轮 Gateway 集群状态是 **ENVIRONMENT BLOCKED / NOT VALIDATED**，不计入通过数。

未重新验证 amd64、XDP 性能、冷文件存储、短连接 / TLS 握手容量、长时间浸泡和云负载均衡。每请求分配减少不代表多租户大量路由的内存规模已经验收；指标句柄缓存也会占用路由级内存。

## 环境与复现

- OrbStack Ubuntu 25.10 / aarch64，Linux 7.0.14，原生 `/tmp` tmpfs。Rust 1.90.0、release thin LTO、单 codegen unit，锁文件不变。
- 正式新旧版本及框架对照均为两个 worker，进程限定在 VM CPU 10,11；wrk 四线程在 2–5；共同使用 OpenResty 1.31.1.1 HTTP 上游，四 worker 在 6–9。另有明确标注的单 worker A/A 使用 CPU 10。
- 每个正式窗口预热 1 秒、测量 6 秒，3 轮、64 / 256 并发，逐场景交替启动新进程并轮换引擎先后。两版使用同一配置及响应内容。每次启动进行完整行为预检，包含分流、POST 完整正文长度 / MD5、TLS、静态正文及响应头。
- 关闭访问日志、OTLP、压缩以及配置的认证 / 限流；rgnix 的正常指标、进程 / 插件预算和沙箱保持启用。NGINX 代理未开启响应内容缓存。最小 Pingora 省略产品策略，不能当成功能等价的替代品。
- 构建、功能回归及 Heaptrack 不与正式窗口并行。保留全部窗口、P99、CPU / 请求、PSS、线程 CPU 及压测输出，不挑选最快结果。进程内存是每窗新进程的测量值，不与旧版混合负载进程的高水位混用。
