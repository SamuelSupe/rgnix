# Hyper 固定成本优化与 Redis 移除 — 2026-10-23

本轮已移除 Redis，并减少固定单 IP 上游的选址锁操作；**尚未测出可信的端到端性能提升**。CPU 与吞吐校准均失败，全部 84 个测量窗口、45,664,443 次零错误请求均保留。

以 GitHub main 的 `a110737b62373c177fe244123bca3e4175005412` 为基线，根据性能分析先落实范围可控的共享状态优化，并按用户要求移除 Redis。完整性能结果及资格结论见下方；历史 NGINX 比率和原型的 +11% 不作为本轮收益。

## 实现范围

- 单个固定 IP 上游在首次选择时缓存端点及原有健康状态，随后选址不再获取进程共享的 pool Mutex。继续调用原有健康判断和租约函数，保留主动检查、被动冷却、weight=0 与后端并发上限。DNS 和多端点选择继续使用原路径；配置快照中的后端仍按既有规则复用或替换。
- 移除 Redis 客户端、协调器、CLI/Helm 入口、协调器指标及验证环境的 Redis 部署依赖。路由的认证前/后限流以及 namespace 总速率继续使用原有本地令牌桶。副本独立计数；N 副本可能达到 N 倍每副本额度，重启会初始化本地桶。迁移要求见[本地限流](shared-rate-limits.md)。旧 CLI 参数被拒绝，Chart 拒绝仍指定 Redis Secret 的配置。
- 锁文件仅删除 Redis 和四个不再需要的依赖，没有升级其余版本。同编译参数的 ELF 从 45,163,272 降至 44,784,632 字节，减少 378,640 字节（0.84%）；这是未 strip 的二进制大小，不等于运行内存收益。

普通 HTTP/1 快路径原来就没有 Redis 查询，因此移除 Redis 不应被解读为替普通代理消除了一次网络访问。策略路径则删去了无协调器时的配置读取与异步策略包装；本地限流仍有其自身同步成本。

原分析中的 owned HTTP/1 原型仍调用 `SendRequest::send_request`，不能直接视为已经消除了所有 channel；连接准入的 semaphore 也不等于每个 HTTP 请求均获取一次。时间读取包含协议和超时用途，不能把所有时钟调用直接压缩为两次。迁入新上游驱动、改 Wasm fuel、分片指标及计时改造均留待独立行为验证和测量，本轮没有同时重写这些边界。

## 产物和方法

两份二进制均在 OrbStack Ubuntu 原生 Linux arm64、Rust 1.90.0 / LLVM 20.1.8 下使用 `cargo build --release --locked --features http3,jemalloc` 构建，默认 thin LTO、codegen-units=1。没有拿历史 Rust 1.98 产物作对照。

| 本轮候选 | `ea77a305961260eaaaaf31e68b695830667f3df28e0c3be85921ff1593d53ca2` |

使用现有 `scripts/benchmark_compare.py` 的真实 socket fixture、预检及采样函数。CPU 同窗诊断让两份产品进程同时竞争 guest CPU 10,11，各两 worker；两组 wrk 使用不重叠并逐轮轮换的 CPU 对，上游使用 CPU 6,7。三轮、每轮两次、64/256 并发，每窗预热 3 秒、测量 12 秒。先用完全相同 ELF 做 A/A，CPU 每请求成本的每对对称差要求小于 3%。同窗吞吐不是各自独占容量。

独立串行吞吐比较使用相同配置、两 worker，显式分开客户端、代理与上游的 guest CPU 集合，轮换执行顺序。每组保留两份同二进制样本作 A/A，三轮累计六窗；要求每个配对的吞吐对称差和组内 CV 均不超过 10%，并且零错误。不删除失败或偏离窗口。guest 绑核不代表独占宿主机物理核心；其他项目没有被停止。

## CPU 同窗 A/A 结果

这轮没有使用候选，而是两边都运行基线 ELF。64 并发六对样本的最大 CPU 成本对称差为 **7.50%**，256 并发为 **20.67%**；两个档位都没有通过事先采用的 3% 门槛。全部 17,666,321 次请求零 wrk 错误，但零错误不能修复测量资格失败。后续串行数据中的 CPU 值只能描述所测窗口，不用于宣称稳定 CPU 收益；本轮没有继续做同窗 A/B 来覆盖这次失败。

## 本地限流策略路径

另在 1 KiB / 64 并发的两份产品配置中同时启用 `rgnix_limit_rate 1000000 burst=1000000 key=route`，触发完整策略路径，又避免额度拒绝影响比较。每份产物各六窗，12 窗累计 4,452,513 次请求，零 wrk 错误。

吞吐中位数从 43,560 到 40,575 req/s（观察值 −6.9%），CPU 从 39.42 到 38.82 µs/请求（观察值 −1.5%）。但基线 / 候选最差 A/A 配对差为 34.37% / 41.90%，CV 为 21.80% / 35.60%，同样未通过资格。这些数字既不能确认为吞吐回退，也不能确认为 CPU 收益。P99 中位数 / 最差从 11.445 / 49.225 到 14.569 / 16.651 ms；PSS 中位数从 30.59 到 30.79 MiB。

因此，本轮确认的是 Redis 移除、原有本地策略保留以及固定单 IP 选址少一次 pool 锁；**尚未测出可信的端到端性能提升**。CPU 同窗和两类串行测量的全部失败资格均保留，不通过重试挑选好看的窗口。

## 行为验证

候选产物在 OrbStack 通过 462 项真实运行检查：默认 Hyper 的基础集成 104、Hyper 专项 68、产品策略 115、显式 Pingora 的基础集成 104、含 HTTP/3 的协议检查 71。覆盖本地 rate/burst/key 隔离、认证顺序、租户配额、热更新、HTTP/2、gRPC、WebSocket、取消、无重放及排空。release 库测试 26 通过、1 忽略；新增回归保护固定端点的健康检查、被动冷却和容量限制。

Helm 的 Ingress/Gateway × Hyper/Pingora 四种渲染、两个旧配置拒绝场景及 lint 均通过。额外启动检查确认两个独立启动的实例均分别返回 200/429，带令牌读取的 `/v1/config.rate_limit_scope` 为 `process`，旧 Redis CLI 参数以退出码 2 被拒绝。该检查最初遗漏管理令牌，被正常的诊断鉴权边界拒绝；配置测试令牌后通过。Rust 格式、Python/JSON/Shell/YAML 语法和 diff 检查通过。Gateway 双副本脚本已改为分别断言每个副本获得自己的 200/429 额度，但本轮没有运行 Kubernetes 多副本 E2E。

没有执行新版本的 24 小时混合长测、原生 amd64、Bookworm 发行镜像和物理 NIC 验收。历史 Redis 503 的原始长测失败仍保留，移除依赖不能把此前失败转换为长测通过。
