# 第四轮性能优化：Gateway 路由索引（2026-09-27）

本轮将 Gateway 的全量规则扫描改为按监听器、域名、路径查找候选，优先级在配置发布前排序；匹配阶段按需解析 query，一次请求复用同一解析结果。只有一条规则时直接匹配。改动基于[第三轮](validation-performance-round3-2026-09-27.md)源码，尚未提交或发布；v0.4.0 下载和镜像不包含本轮优化。

**结果分开解释：** 1,000 条无 query 路径规则的匹配微基准从 5.190 µs 降至 0.115 µs，约快 45.2 倍。真实 Gateway 的同规模场景，本次三轮吞吐中位数上升 51.4%，CPU/请求下降 34.1%。但端到端 A/A 最大成对差异为 21.3%，仍未通过整机性能发布门槛。微基准倍数不能当成 HTTP 吞吐倍数，本轮也没有重新进行 NGINX/OpenResty 前端对比。

## 实现与行为边界

- 不同监听地址分开索引；优先选择具体域名，再按通配域名后缀匹配。保留更具体监听器没有路由时不回退到其他监听器的规则。
- 精确路径和路径段前缀分别索引；同组规则按路径、方法、header/query 条件数量及原有资源优先级排序。保留尾斜杠、同优先级取舍和重复 query 参数首值生效的现有行为。
- header 条件名在控制面转小写；不带 query 条件的候选跳过解析。有 query 条件时，一次匹配共享解析结果。
- 索引随不可变快照发布；旧快照不被原地修改。管理接口按命名空间过滤路由后重新建立索引，防止候选位置仍指向已隐藏的条目。编译后的索引不进入配置 JSON 或指纹。
- 相同域名、相同路径下大量重叠的 query/header 条件仍可能逐条筛选；gRPC service/method 没有独立索引。

## 路由匹配微基准

[全部原始窗口](validation/performance-round4-routing-2026-09-27.json)。旧扫描实现原样保留为测试 oracle，与新索引在**同一个 release 测试程序**中比较；测试包含 1 / 100 / 1,000 / 10,000 条规则，8 个请求轮换命中首尾及中间位置。每个实现先预热 500 ms，再交替运行三个 500 ms 窗口；每 16 次查找读取计时器，使用 `black_box` 保留工作。下表为三轮中位数，包含测试循环与计时成本，不包含 HTTP I/O。

| 场景 | 规则数 | 旧扫描 µs/匹配 | 新索引 µs/匹配 | 加速比 |
| --- | ---: | ---: | ---: | ---: |
| 不同路径，无 query | 100 | 0.491 | 0.089 | 5.5× |
| 不同域名，无 query | 100 | 0.962 | 0.069 | 13.9× |
| 同一路径，以 query 选择规则 | 100 | 10.769 | 0.550 | 19.6× |
| 不同路径，无 query | 1,000 | 5.190 | 0.115 | 45.2× |
| 不同域名，无 query | 1,000 | 9.790 | 0.075 | 129.9× |
| 同一路径，以 query 选择规则 | 1,000 | 105.345 | 4.350 | 24.2× |
| 不同路径，无 query | 10,000 | 127.107 | 0.133 | 955.6× |
| 不同域名，无 query | 10,000 | 178.590 | 0.084 | 2123.1× |
| 同一路径，以 query 选择规则 | 10,000 | 1218.054 | 88.033 | 13.8× |

另有带无关、编码及重复参数的 query 请求，全部数据保留在 JSON 中。相同新实现的 A/A 最大成对差异为 1.97%，最大组内 CV 为 1.99%。

初版索引在单规则场景多出约 23 ns；增加直接匹配分支后，最终版本仍有如下小规模额外成本：

| 单规则场景 | 旧扫描 ns/匹配 | 新实现 ns/匹配 | 差值 ns |
| --- | ---: | ---: | ---: |
| 路径，无 query | 20.1 | 24.9 | +4.7 |
| 域名，无 query | 19.3 | 28.7 | +9.4 |
| 需要 query 条件 | 118.7 | 125.0 | +6.3 |

本次单次索引构建测量最大为 5.76 ms（10,000 条规则）；这只是所测数据分布的控制面成本，没有覆盖全部配置组合。索引需要额外 O(N) 存储，尚未单独测量其堆占用。

## 真实 Kubernetes Gateway 端到端对照

[原始记录](validation/performance-round4-gateway-2026-09-27.json)包含 **18 个窗口、4,945,710 次请求、HTTP/连接/读写/超时错误 0**。两版使用同一组实际 Kubernetes HTTPRoute、Service 和 EndpointSlice；1,000 条路径规则分布在 63 个 HTTPRoute 中。每窗前检查首、中、尾三条路径，压测命中末条路径的子路径并携带相同 query。

| 规则数 | 吞吐 req/s：旧 → 新 | 吞吐变化 | CPU µs/请求：旧 → 新 | P99 ms：旧 → 新 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 51,576 → 52,362 | +1.5% | 19.36 → 19.04 | 2.09 → 2.15 |
| 1,000 | 29,950 → 45,333 | +51.4% | 33.34 → 21.98 | 4.38 → 2.89 |

三轮逐对吞吐增幅（1,000 规则）为 61.1%, 51.4%, 57.0%。这些是本次样本的观察，不是稳定容量承诺。单规则吞吐中位数只相差约 1.5%，不据此认定提升。1,000 规则下新进程 PSS 为 79,623–81,569 KiB，旧进程为 79,585–81,409 KiB，区间重叠；没有稳定内存下降的证据。

同一最终二进制 A/A 的最大成对吞吐差异为 **21.26%**，最大组内 CV 为 **18.59%**，超过各 10% 的既有门槛；因此**整机性能发布门槛仍未通过**。A/A 最大单窗 P99 为 7.86 ms，普通 A/B 最大单窗 P99 为 6.09 ms；原始记录包含全部 18 个窗口。

## 正确性验证

[验证记录与源码摘要](validation/performance-round4-regression-2026-09-27.json)：**235 项定向检查通过**，包括 Rust 16、HTTP/TLS/正文/静态/热更新 92、产品功能 111，以及实际 Gateway 16。Rust 路由对照测试内部比较 1,650 组输入，包括监听器隔离、域名与路径优先级、尾斜杠、UTF-8、方法、header、重复/编码 query、gRPC 匹配和空路径。另验证旧快照仍可使用、命名空间视图不泄露路由，以及 reindex 不改变配置指纹。

真实 Gateway 验证通过了路由匹配、跨租户模拟授权、端点撤销/恢复、路由修改/删除。本轮使用 headless Service 绕过已耗尽的 Service 地址池，通过原生 Linux 进程连接实际 OrbStack Kubernetes API；测试没有部署 Helm 控制器 Pod。两个测试命名空间、GatewayClass 及临时凭据已清理，Service 数量回到测试前的 128。

Release all-targets Clippy（拒绝 warning）、格式和 diff 空白检查通过；246 个构建源码、清单与验证文件在 macOS 工作区和 Linux 副本中摘要一致。未重复完整的 Helm Gateway 部署、Gateway HTTP/2/gRPC 网络流、TLS Secret 轮换和滚动升级；独立 OTLP 套件、amd64、长时间浸泡和物理主机容量也不在本轮验证范围内。普通 HTTP/2 协商及正文转发包含在上述 92 项集成检查中。

## 环境、复现与产物

- OrbStack Ubuntu / aarch64，Linux 7.0.14，Kubernetes v1.35.6+orb1，Rust 1.90.0。release、thin LTO、单 codegen unit，Cargo.lock 不变。
- 原生 tmpfs 中构建与测试；微基准固定 VM CPU 10。端到端一个 rgnix worker 在 CPU 10，wrk 两线程在 2,3，共同 NGINX 1.30.5 上游两个 worker 在 6,7。HTTP/1.1 keepalive、64 并发、2-byte 响应，预热 3 秒、测量 6 秒，每窗重启代理；两版按轮次交替先后。
- 关闭访问日志、OTLP 导出；常规 rgnix 指标和正常代理处理保留。功能回归、构建和采样器没有与正式窗口并行。
- [本次集群验证脚本原件](validation/performance-round4-gateway-fixture-2026-09-27.py)保留固定 OrbStack API 转发、路径及命名空间，用于审计与复现该环境；它读取私有、minify/flatten 后的 kubeconfig，不包含集群凭据。首次命名空间创建冲突会停止，不会复用其他工作负载。运行时需要本报告的两个二进制和 NGINX 上游；它不是通用部署工具。
