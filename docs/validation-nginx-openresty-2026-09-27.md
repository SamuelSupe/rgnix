# rgnix / NGINX / OpenResty 性能对比 — 2026-09-27

后续未发布源码的优化见[数据面优化报告](validation-performance-2026-09-27.md)，当前第七轮源码的直接对照见[最新 NGINX 测试](validation-nginx-round7-2026-09-27.md)。本文保留已发布 v0.4.0 的原始结果。

**当前 rgnix 在本次所有可比场景中的吞吐都明显低于 NGINX/OpenResty，每请求 CPU 成本和混合负载内存高水位也更高。** 64 并发普通 1 KiB 代理中，rgnix 为 50,287 请求/秒，NGINX/OpenResty 分别为 154,586 / 191,479，约为 rgnix 的 3.1 / 3.8 倍。静态文件差距更大，约为 7.2 / 9.2 倍；请求头分流时 OpenResty Lua 约为 RGL 的 5.0 倍，POST 前缀分流约为 2.6 倍。

各场景、各并发下，NGINX/OpenResty 三轮中的最低吞吐仍高于 rgnix 的最高吞吐，因此这组数据支持“大幅差距”的判断。共享环境仍使绝对数值波动，不能精确排名 NGINX 与 OpenResty，也不能据此给出生产容量保证。无插件路径已经存在明显差距，后续优化应同时评估基础代理、静态文件和插件路径的 CPU 成本；本次没有做调用栈剖析，尚未定位到具体函数。

本次测试使用已发布的 **rgnix v0.4.0**，源码提交 `464a43a4e6f40bd2b219848b6b54237d7048d8d6`，没有修改生产代码。对手为 **NGINX 1.30.5** 和 **OpenResty 1.31.1.1**（内含 NGINX 1.31.1、LuaJIT 2.1-20260415）。这是三个固定版本产品的数据面对比；两个 NGINX 内核版本不同，不能把差异全部归因于 Lua。

完成 **120 个正式测量窗口、156,375,755 次请求，HTTP 状态、连接、读、写和超时错误计数全部为零**。三者每次启动后均通过状态码、正文、分流后端及请求头预检；POST 正文通过完整长度及 MD5 校验。共 9 次前端启动，每次均重新验证 TLS、普通代理和各自配置的分流行为。

[完整原始数据、逐轮统计、配置、脚本及二进制身份](validation/nginx-openresty-2026-09-27.json) · [可复现压测脚本](../scripts/benchmark_compare.py)

尾延迟存在明显异常窗口：NGINX 256 并发 1 KiB 代理第三轮 P99 为 41.703 ms，OpenResty 64 并发 HTTPS 第一轮为 29.031 ms，OpenResty 256 并发 POST 第一轮为 37.340 ms。它们全部计入原始结果，未删除。2 B 直接响应在 64 并发下，rgnix 的 P99 中位数反而低于另两者，不能把吞吐差距概括为“所有延迟都更差”。本次不足以确定这些偶发尾延迟的原因。

| 服务 | PSS 峰值 | RSS 合计峰值 |
|---|---:|---:|
| rgnix | 160.5 | 162.1 |
| nginx | 32.5 | 48.4 |

- 宿主机：Mac17,7，18 个逻辑 CPU，64 GiB RAM；OrbStack 2.2.3。
- Linux：Ubuntu 25.10，aarch64，`7.0.14-orbstack-00380-ga7e0a2dc9535`。文件、源码构建和运行目录在 Linux 原生 `/tmp` **tmpfs**，没有从 macOS 共享目录读取计时中的静态文件；这是内存文件系统上的热文件测试，不衡量磁盘性能。
- 服务：2 个 worker / 线程，固定 VM CPU **10,11**；wrk：4 线程、CPU **2,3,4,5**；上游：4 个 OpenResty worker、CPU **6,7,8,9**。它们互不重叠，但没有独占物理宿主机。

- wrk `4.1.0-4build2`；NGINX/OpenResty 禁用访问日志、gzip、代理请求/响应缓冲和上游重试，开启 sendfile、HTTP/1.1 上游连接复用及 60 秒 keepalive。rgnix 禁用访问日志、OTLP 输出、压缩及配置的鉴权限流；内置指标与请求/插件预算仍工作。
- 所有前端使用同一组本机上游，传输走 `127.0.0.1`。HTTPS 场景仅客户端到前端使用 TLS，前端到上游仍用 HTTP。三者预检均协商 TLS 1.3 / TLS_AES_256_GCM_SHA384；证书为本次生成的自签名测试证书。未测连接握手峰值或上游 TLS。
- 每轮服务顺序依次为 rgnix→NGINX→OpenResty、NGINX→OpenResty→rgnix、OpenResty→rgnix→NGINX；第二轮反转场景及并发顺序。

## 正文分流与脚本语义

请求头场景按 `x-canary` 在两个后端之间交替选择，并向上游设置 `x-selected`。POST 场景每次上传 65,536 字节：一类在开头放 `route=canary;`，另一类将同一标记放到第 1,025 字节。两种实现都只搜索前 512 字节，因此第二类应进入 primary；完整正文仍送达后端。

RGL 使用 `rgnix_request_body prefix 512`。OpenResty 使用 `ngx.req.read_body()`、`ngx.req.get_body_data()` 后取前 512 字节，配置 128 KiB 内存缓冲以避免本次 64 KiB 请求落盘。这是**路由结果相同、读取机制不同**的产品功能对比，不应宣称两者执行相同的 I/O 算法。正文完整性验证在计时前完成；计时中不计算 MD5，也不逐个解析响应正文，避免把验证器算进吞吐。

本次客户端在回环网络上连续发送正文，未测慢速上传时提前选择上游或首字节延迟的表现，也未测更大请求体的内存差异。

RGL 加载时编译 Wasm，保留每请求实例隔离和资源限制；OpenResty 采用每 worker 共享 LuaJIT VM、请求协程上下文，没有在本次配置中额外模拟 RGL 的 fuel/内存限制。两者的性能与隔离保证应分开评估。[OpenResty 执行模型与正文 API](https://github.com/openresty/lua-nginx-module#description)。

## 复现

从 [NGINX 官方源包](https://nginx.org/download/nginx-1.30.5.tar.gz)、[OpenResty 官方源包](https://openresty.org/download/openresty-1.31.1.1.tar.gz) 和 [rgnix v0.4.0 release](https://github.com/SamuelSupe/rgnix/releases/tag/v0.4.0) 获取这三个固定版本。校验原始数据中记录的 SHA-256。NGINX 的构建选项为 `--with-http_ssl_module --with-http_v2_module --with-cc-opt=-O2`；OpenResty 使用相同显式选项和默认模块，分别安装到独立前缀目录。构建完成后再压测。

在有 wrk、OpenSSL CLI、Python 3、taskset 的 Linux 中执行，并根据可用 CPU 修改列表。工作目录必须是尚不存在的 Linux 原生目录：

```sh
python3 scripts/benchmark_compare.py \
  --rgnix /path/to/rgnix \
  --nginx /path/to/nginx/sbin/nginx \
  --openresty /path/to/openresty/bin/openresty \
  --server-cpus 10,11 --client-cpus 2,3,4,5 --origin-cpus 6,7,8,9 \
  --workers 2 --origin-workers 4 --client-threads 4 \
  --concurrency 64 256 --rounds 3 --seconds 8 --warmup 2 \
  --work-dir /tmp/rgnix-compare-new --output /tmp/rgnix-compare-new.json
```

脚本生成并保留三份前端配置、上游配置、RGL/Lua 源码与 wrk 请求脚本，按窗口保存原始结果，失败时终止并保留已完成样本；退出时回收本次启动的进程。源码及脚本执行环境使用真实 OrbStack Linux；另执行了 Python 语法检查与 `git diff --check`。没有因为新增压测脚本而重跑无关 Rust 功能套件。

结束后复核了 40 个统计分组，每组恰有三轮、计时均不少于 8 秒、中位数与原始样本一致；复核三份二进制摘要未变化。本次 26 个服务进程已退出，五个监听端口均关闭。

未验证：独占裸机、Linux amd64、固定 RPS 的开放环 SLO、HTTP/2、WebSocket、gRPC、真实 NIC/XDP、多机网络、Kubernetes 控制器扩容、长时间稳定性和故障期间容量。这些不能从本次本机 HTTP/1.1 结果推导。
