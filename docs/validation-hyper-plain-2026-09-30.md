# Hyper 精简执行路径与连接驱动试验

2026-09-30，`experiment/replace-pingora`，基于 `1bd974f` 的本地未提交改动。默认数据面仍是 Pingora。

**保留普通 HTTP/1 代理和固定响应的精简路径：1 KiB 代理分配调用从约 30.53 降至 17.60 次/请求，减少 42.34%。吞吐对照没有通过完整校准，不能宣称稳定吞吐提升或接近 NGINX。前台连接驱动试验已经撤下。**

## 保留的实现

配置发布时识别可使用精简路径的路由，提前准备固定响应状态、头部和 `Bytes` 内容。普通代理直接使用已准备的后端、客户端及固定请求/响应头，不构造完整 `Context`、插件输入、原始 URI、客户端地址、请求方法和后端名称的逐请求副本。

适用范围是 HTTP/1.1、固定 `return` 和不带 URI 的 `proxy_pass`；后端使用轮询或最少连接、上游 HTTP/1。访问日志、trace、脚本、租户治理、认证、限流、可信代理/访问规则、灰度、Gateway、压缩及含变量的配置使用原有完整路径。请求携带 `traceparent`、gRPC 内容类型或升级头时也保留完整路径。没有为了测量而关闭已经配置的功能。

精简路径继续使用原来的流式请求 body、大小限制、上游连接池、TLS 校验、读写超时、被动健康检查和禁用重试规则。每个请求仍持有自己的快照、请求预算和后端租约。响应 body 与完成队列共用；计数在实际 socket flush 后提交，取消时记录错误并释放资源。普通路径归一化可借用原字符串，编码或复杂路径仍按原规则处理。

## 分配验证

OrbStack Linux AArch64；对 jemalloc 分配/重分配入口做探针。单持久连接预热十次，再执行 500 次 1 KiB 请求，逐次检查状态和完整响应。探针与吞吐窗口分开，不包含嵌套分配器入口，没有丢失事件。

| 指标 | 优化前 | 保留方案 | 变化 |
|---|---:|---:|---:|
| 分配/重分配调用 / 请求 | 30.526 | 17.600 | −42.34% |
| 累计申请字节 / 请求 | 5,622.936 | 4,636.828 | −17.54% |
| 逐请求状态对象申请大小 | 1,072 B | 192 B | 精简完成状态 |

累计申请字节不是常驻内存，也不能换算成吞吐百分比。探针包含少量后台申请；这里的状态大小来自实际分配事件，不是对完整进程内存的估计。

## 保留方案与 NGINX 对照

优化前、保留方案和 NGINX 1.28.0 使用相同配置和共同 NGINX 源站，两个前端 worker，64/256 并发；每程序每轮两个窗口，三轮、预热三秒、测量十二秒，轮换顺序。共 **72 窗、183,551,666 请求、零错误**。

**所有组均未通过完整 A/A 校准。** 下表只记录观测中位数；不认定稳定收益、稳定退化或容量。固定响应在 64 并发的观测值更低，也保留在报告中。

| 场景 | 并发 | 优化前 req/s | 保留方案 req/s | NGINX req/s | 保留方案相对优化前 |
|---|---:|---:|---:|---:|---:|
| 2 B 固定响应 | 64 | 242,137 | 224,614 | 601,973 | −7.24% |
| 2 B 固定响应 | 256 | 220,828 | 281,520 | 477,608 | +27.48% |
| 1 KiB 代理 | 64 | 79,112 | 84,277 | 161,516 | +6.53% |
| 1 KiB 代理 | 256 | 63,413 | 70,316 | 126,150 | +10.89% |

| 场景 / 并发 | 保留方案 / NGINX CPU µs/请求 | 最大窗口 P99 ms | 保留方案峰值 PSS MiB |
|---|---:|---:|---:|
| 固定响应 / 64 | 8.45 / 3.32 | 1.967 | 31.50 |
| 固定响应 / 256 | 7.07 / 4.13 | 2.627 | 42.97 |
| 1 KiB 代理 / 64 | 23.04 / 12.28 | 3.159 | 34.61 |
| 1 KiB 代理 / 256 | 27.95 / 15.78 | 14.841 | 53.82 |

P99 是窗口最大值，不是合并全部请求的分位数，也不是相同到达速率下的延迟比较。NGINX 256 并发代理有一个 81.537 ms P99 窗口，原始记录未删。没有证明 PSS 改善。

A/A 要求至少三对同一程序窗口、零错误，每对 RPS 对称差和两列样本 CV 都不超过 10%。本轮优化前代理 64 并发最大配对差为 83.08%；保留方案对应值为 25.64%，组 CV 最大 30.03%。宿主其他构建与文件同步仍在运行，虚拟 CPU 绑定不保证物理核心独占；不能把波动直接归因于某个代码改动或宿主进程。

## 撤下的连接驱动试验

另一个不可变二进制尝试在等待上游响应头时由当前请求任务直接推进连接，完成/取消后交还后台。仍保留 Hyper 请求队列与响应回调，并增加了连接状态的同步锁、前台驱动 future 和任务交接；不是固定 worker，也没有消除通道。

初版虽通过 265 项功能检查，但 64 并发正式窗口出现 **127 个读错误和 5 个状态错误**，测试立即停止。发现后台只在前台持有期间保存唤醒句柄；空闲时没有保存自己的句柄，前台替换 socket/dispatch waker 后，部分 body 无法继续推进。修正为始终保留后台句柄，并在完成/取消后唤醒它。

新增回归覆盖后台未在前台持有期间得到轮询的时序：未修正代码在独立副本中超时，修正后通过，覆盖正常完成和取消。修正后二进制再次通过 265 项运行检查、28 项连接/池单元测试（2 项原有忽略），64/256 并发短负载复验零错误。

随后独立执行保留方案、修正后的驱动及 NGINX 对照：**36 窗、52,924,674 请求、零错误**。所有组仍未通过完整校准。

| 1 KiB 代理 | 保留方案 req/s | 前台驱动 req/s | NGINX req/s | 驱动相对保留方案 |
|---|---:|---:|---:|---:|
| 64 并发 | 96,151 | 83,830 | 178,055 | −12.81% |
| 256 并发 | 97,766 | 82,841 | 189,913 | −15.27% |

驱动探针累计申请约 5,102.94 B/请求，高于保留方案约 4,636.83 B/请求。观测没有提供保留新增复杂度的收益依据，因此撤下实现和默认启用调用。不能把表中差额解释成锁造成的稳定退化；要进一步改变执行模型，需要直接验证 worker/连接归属和通道消除，而不是在共享后台连接上增加前台同步借用。

修正后的[试验补丁及回归测试](validation/hyper-inline-driver-rejected-2026-09-30.patch)、[失败窗口](validation/hyper-plain-driver-bug-2026-09-30.json)、[修正后完整窗口](validation/hyper-plain-driver-rejected-2026-09-30.json)均归档；补丁不属于当前运行代码。不同阶段的观测值不能相减或合并计算总收益。

## 实际检查与证据

- 保留方案：Hyper HTTP 集成 98、产品能力 115、双 worker 生命周期 52，共 **265 项运行检查通过**。新增测试保护固定响应 HEAD 长度、热更新引入限流、旧普通代理快照完成和动态响应变量恢复。
- 默认 Pingora：另跑 **98 项 HTTP 集成检查通过**，验证共享完成统计和路径归一化没有破坏默认模式。
- 保留源代码恢复到已验收的精简方案，重跑全 target Clippy `-D warnings`、默认构建检查、release 构建、格式及 diff 检查。恢复后的 release 摘要与被测保留方案一致。
- 上述运行检查覆盖 body/头部/URI、TLS、HTTP/2/h2c、gRPC/trailers、WebSocket、认证、RGL、租户策略、取消、超时、热更新、预算释放及优雅退出。没有新跑 Kubernetes 控制器、amd64、HTTP/2 吞吐、新 TLS 握手吞吐、固定到达速率延迟或长期生产负载。

构建条件为 Rust 1.90.0、release/thin LTO/单 codegen unit、`hyper-experimental,jemalloc`；Linux AArch64。前端 CPU 10～11，客户端 CPU 2～5，源站 CPU 6～9；NGINX 关闭代理缓冲和请求重试，Host、超时和池容量对齐。这里没有 OpenResty 前端比较。
