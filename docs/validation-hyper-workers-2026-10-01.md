# Hyper worker 归属与 NGINX 对照（2026-10-01）

本轮把实验性 Hyper 的 worker 改为独立单线程 reactor，显式 HTTP/1 上游客户端池也归属同一 worker。完整产品观测吞吐中位数提高约 33% / 23%，跨线程同步调用明显减少；**所有吞吐组均未通过 A/A 校准，不能认定稳定提升、NGINX 性能对等或生产容量**。改动保留在实验分支，默认数据面仍为 Pingora。

## 选择这个优化的依据

[上一轮剖析](validation-hyper-deep-2026-10-01.md)中，减少请求复制并没有显著提高普通代理吞吐；网络读写次数也没有比 NGINX 多一倍。双 worker 的共享 Tokio 调度器和 HTTP/1 池仍有同步和任务转移成本。本轮优先调整连接与池的归属，没有重写 HTTP parser 或绕开已有策略。

先用独立原型的 `--local-workers` 验证方向：相同原型 ELF，双 worker / 64 并发，三轮、每程序每轮两窗，预热两秒、测量八秒。共享模式中位数 93,887 req/s，独立 worker 模式 125,611，NGINX 150,485。18 窗、17,879,426 请求、零错误；三组校准都失败。因此它只用于选择候选，不能替代完整产品结果。[原始窗口](validation/hyper-workers-prototype-2026-10-01.json)、[校准分析](validation/hyper-workers-prototype-analysis-2026-10-01.json)。本轮原型使用 legacy 客户端，没有启用已有的 `--owned-http1`。

## 实现与边界

- 每个配置监听器按 `threads` 创建独立单线程服务。Linux 使用 SO_REUSEPORT 分配新连接；HTTP/1 请求、连接 driver 和显式 HTTP/1 池在接受连接的 worker 上执行，减少共享调度和池锁竞争。
- 第一个 worker 先独占绑定，再允许后续 worker 加入。第二个 rgnix 进程不能意外加入已有监听端口。`listen 0` 的后续 worker 使用第一个 socket 已分配的实际端口；路由匹配继续使用配置中的监听器身份。
- 传输设置、TLS 验证上下文和固定首部在控制面准备。客户端在对应 worker 首次使用时创建；相同配置 profile 在该 worker 内复用。共享的空闲上游总预算没有增加，显式 HTTP/1 每个池的单端点上限按 worker 划分。
- HTTP/2 和 ALPN Auto 继续使用一个共享客户端，以保留跨 worker 多路复用。初版曾把它们也拆成独立池，原有“同一上游连接”验收失败；已经恢复共享，原断言保留并通过最终验收。
- 进程连接、请求、租户和后端预算继续共享；禁止请求重放、超时、取消、旧请求快照和优雅终止规则保留。非 Linux 通过克隆同一接受 socket 运行，未在本轮验证。

归属固定也有取舍：长期连接负载不均会影响 worker 利用率，HTTP/1 空闲池不跨 worker 借用，池元数据随活跃 worker/profile 增长。本轮的小配置 PSS 结果不能代表大型租户配置。源码增量基于开始时的脏工作区，见[本轮补丁](validation/hyper-workers-local-2026-10-01.patch)；没有重置已有改动。

## 完整产品吞吐对照

OrbStack Ubuntu 25.10 / Linux ARM64，Rust 1.90，同工具链 release + `hyper-experimental,jemalloc`。旧版 ELF 是上一轮最终保留版本，候选为本轮最终构建。共同源站和 NGINX 前端均为 NGINX 1.28.0；没有 OpenResty 前端比较。配置为共同的普通 HTTP/1 代理、1 KiB 响应、禁用自动重试和代理缓冲。

前端两 worker、CPU 10～11；客户端四线程、CPU 2～5；源站四 worker、CPU 6～9。三轮轮换程序顺序，每程序每轮两个窗口，预热三秒、测量十二秒，64 和 256 并发分别校准。源站直连为约 339,988 req/s；正式窗口源站/客户端占用及线程、连接获取计数均保留。

## 同步与剩余成本

吞吐测量全部结束后，另开预热后的 12 秒 perf syscall 窗口；以下是仪器窗口的操作数，不是稳定吞吐或等待时间的证明。

| 操作 / 请求 | 优化前 | 候选 | NGINX |
|---|---:|---:|---:|
| futex | 0.033983 | 0.000450 | 0 |
| 上下文切换 | 0.020246 | 0.007147 | 0.006384 |
| recvfrom | 2.001196 | 2.001642 | 2.002165 |
| writev | 2.000983 | 2.001479 | 2.002115 |
| epoll_pwait | 0.055881 | 0.103580 | 0.124124 |

futex 调用约减少 98.7%，上下文切换约减少 64.7%，支持减少共享调度/池同步的方向；不是“CPU 或锁等待减少 98.7%”。候选的 epoll 调用增加，不能说所有调度操作都减少。候选和 NGINX 各有少量新建连接，未观察到持续逐请求建连。[优化前 syscall](validation/hyper-workers-syscalls-before-2026-10-01.json)、[候选和 NGINX](validation/hyper-workers-syscalls-local-2026-10-01.json)。

另外各取 15 秒、199 Hz CPU-clock / DWARF 栈，两个程序均未丢样本。候选 flat DSO 分布约为内核 52.09%、rgnix 38.16%、libc 5.32%、vDSO 4.44%；NGINX 为内核 72.15%、NGINX 19.28%、libc 8.54%、vDSO 0.03%。仍可见 legacy 客户端 future、前后端 HTTP/1 状态机、首部解析/编码、引用计数/原子操作以及请求生命周期。这些采样比例和 inclusive 栈有重叠，不能换算为独立加速上限；TCP 可读唤醒也不能全部归为 Tokio 浪费。[候选 / NGINX 剖析](validation/hyper-workers-profile-local-2026-10-01.json)。

下一项优先评估 HTTP/1 客户端 dispatch / 响应回调和通用 future 的固定成本，同时保留 framing、背压、升级、取消和禁用重放契约。当前仍有请求通道，已有独立 owned-connection 原型尚未迁入产品。精确时钟只占部分采样，不能凭 NGINX 的缓存时间方式忽略超时或把全部差距归于时钟。

## 实际验证与未解决问题

最终 ELF SHA-256：`30b0882c80645d6e895818df2020340e62451fbf3fa39b00063d30164cb470d3`。锁文件仅增加直接 socket2 依赖，复用已锁定版本，没有升级其他依赖。

- 最终 native 单 worker 生命周期 **56** 项、双 worker + `listen 0` **57** 项、综合集成 **99** 项、完整产品 **115** 项，共 **327 项通过**。覆盖 HTTP/2 复用/流控/期限、共享连接及请求/后端预算、流式上传、取消、WebSocket、重载、回退、旧流结束、TLS/mTLS、插件、鉴权和遥测。
- 最终格式检查、Hyper + jemalloc 全目标 Clippy `-D warnings` 通过；默认构建检查也通过。静态检查单独记录，未作为运行验收计数。
- 更早的候选完整产品测试曾在 CA 轮换后的旧 TLS 连接上收到 reset，预期为 403。重放原有产品主阶段时，**旧版也出现相同 reset**；候选两轮和旧版另一轮通过，简化探针两程序均返回 403。探针使用的中间候选 ELF 已另存并记录摘要。最终完整产品通过，**没有修复或解释这个偶发问题，也不能据此断言它与本轮改动无关**。
